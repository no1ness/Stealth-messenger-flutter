# Eager field-init in WebRTCCallScreen blew up widget tests via PocketBase env read

**Date:** 2026-04-30 13:29
**Files:** client/lib/ui/screens/webrtc_call_screen_native_impl.dart, client/lib/ui/screens/webrtc_call_screen_web.dart, client/lib/supabase_service.dart
**Severity:** medium

## Problem

`webrtc_call_screen_semantics_test.dart` (Requirements 5.1–5.4 — accessibility labels Hang up / Mute / Speaker / Call status) regressed to red after migrating call signaling from Supabase to PocketBase. Symptom: `find.bySemanticsLabel(RegExp('Hang up'))` returned 0 widgets — the Scaffold never rendered, so no semantics tree ever existed.

## Root Cause

`_WebRTCCallScreenState` declared `final WebRtcSignalingService _signaling = WebRtcSignalingService();` as a State field. The `WebRtcSignalingService()` default constructor falls back to `PocketBaseClient.instance.pb`, and `PocketBaseClient.instance` synchronously reads `dotenv.env['POCKETBASE_URL']`, throwing `StateError` when the URL is missing.

In production this is gated by `main.dart` (validates `POCKETBASE_URL` before reaching any screen). But in widget tests `dotenv` is never loaded. The State's field initializer therefore threw at `createState()` time, before `build()` ever ran. The Supabase predecessor had a `setUpAll` hook calling `Supabase.initialize(fakeUrl)`, so the equivalent `_supabaseService = SupabaseService()` field worked. The migration kept the same shape but lost the implicit "test-environment-safe" default — a hidden coupling between the widget and a global env-loader.

The web variant (`webrtc_call_screen_web.dart`) had the identical pattern; no test exercised it directly, so the same latent crash shipped silently.

## Solution

Made `_signaling` nullable (`WebRtcSignalingService? _signaling;`) and instantiate it inside `_startCall()` after the synchronous gate that's already there (permission check on native, `getWebRTCSupport()` on web). Updated downstream usages: `dispose()` and `_hangUp()` use `?.` (defensive — they can fire before `_startCall` reaches the instantiation point); the in-call callbacks (ICE, offer, answer) use `!` because they only fire after a successful `_createPeerConnection`, which itself runs after instantiation.

Also dropped a pre-existing unused `final start = now.subtract(...)` in `SupabaseService.getWeeklyActivityBars` (the only other live `flutter analyze` warning unrelated to this regression).

Verified:
- `webrtc_call_screen_semantics_test.dart` — passes
- Full `flutter test` — 36 passed, 1 skipped, 0 failed (was 35 ~1 -1)
- `flutter analyze` — 1 issue down to unrelated pre-existing `const_with_non_const` in `liquid_contacts_screen.dart`

## Prevention

- **Stateful widgets must not access dotenv/env-dependent singletons in field initializers.** The State's constructor runs synchronously before `build()` and any test fixture's `setUpAll`. If a service depends on global config, instantiate it inside `initState`/lifecycle hooks (where async setup and try/catch can wrap the failure), or pass it in via the widget constructor (DI).
- **Default-parameter singletons hide eager work.** `WebRtcSignalingService({PocketBase? pb})` looks pure but evaluates `PocketBaseClient.instance.pb` on every `WebRtcSignalingService()` call. Whenever a `??` default reaches a singleton that touches env/config, treat the constructor as side-effecting.
- **When migrating a service that has tests, run the relevant test file (not just the new ones) before claiming the migration is done.** The unit tests for the new `WebRtcSignalingService` passed; the *consumer* widget test silently regressed because no one ran the full suite at the right point in `/aif-implement` flow.
- For widget tests of screens that depend on env-loaded services: the alternative is `dotenv.testLoad(mergeWith: {...})` in `setUpAll`. We chose the lazy-init path because it also makes the production code more robust against missing env at runtime (e.g., per-feature flags, A/B), not only a test convenience.
