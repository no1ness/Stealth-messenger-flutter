## Problem

Входящие звонки не доходили до callee. Caller успешно отправлял `offer` в `rtc_signaling`, но receiver-сторона никогда не получала SSE-событие. На web-устройствах вдобавок падал `RTCPeerConnection` с `TURN server with empty username or password` при пустых TURN-credentials.

## Root Cause

Две связанные проблемы:

1. **Неверное представление о PocketBase identity contract.** Документация утверждала, что `users.id` принимает кастомный id длиной «15+ chars». На практике PocketBase требует **ровно 15 символов** по алфавиту `^[A-Za-z0-9_]{15}$`. Прежняя реализация `pbIdFromLocalUuid` отдавала 32-символьный UUID без дефисов → сервер молча отбрасывал клиентский `id` и присваивал свой auto-id. Локально мы продолжали записывать `creator/target` как 32-char stripped UUID, а `auth.id` был 15-char auto-id — strict rule `@request.data.creator = @request.auth.id` валил `create`, а listRule `target = @request.auth.id || creator = @request.auth.id` фильтровала всю входящую SSE-подписку callee. Это race без race condition — баг по согласованию контракта.
2. **`IncomingCallSignalingService.start()` подписывался ДО аутентификации.** SSE-канал в PocketBase привязывает identity на момент handshake. Если в этот момент `authStore` пустой — listRule с `auth.id` всегда false, и события никогда не доходят, даже если send-сторона починена.

Дополнительные следствия первой проблемы:
- 15-char SHA-256 префикс — лоссовая функция, обратное преобразование `pbId → uuid` невозможно алгоритмически. Это ломало старый `localUuidFromPbId` и downstream-код, который полагался на матч `message.creator == knownContactUuid`.
- Глобальный `PocketBase` singleton делится между `WebRtcSignalingService` и `IncomingCallSignalingService`. Их раздельный `_ensureAuth` создавал race на первом старте сессии (два конкурентных `users.create` под одним email).

## Solution

1. **15-char детерминированный hash.** `pbIdFromLocalUuid(localUuid)` теперь возвращает первые 15 hex-символов `SHA-256(localUuid)`. Non-UUID input идёт passthrough (для тестовых fixtures типа `user-A`, `smoke_a_<stamp>`). Константа `kPbIdLength = 15` + pinned test закрепляют алгоритм от случайной смены.
2. **`PbUserIdResolver`** для обратного lookup. Конструктор хеширует все известные UUID (self + контакты), `localUuidFromPbId(pbId)` — O(1) lookup; unknown ids → passthrough. `RtcMessage.fromRecord(record, resolver: ...)` принимает resolver опционально.
3. **`creatorUuid` в payload `offer`/`hangup`.** Когда caller — незнакомец (нет в контактах callee), resolver не найдёт его UUID. Caller кладёт `_selfUserId` в payload как `creatorUuid`; receiver предпочитает payload над `message.creator` (15-char hash).
4. **Extracted `PocketBaseAuthService` singleton.** Один процесс-wide инстанс делится между двумя signaling-сервисами. In-flight guard защищает от двух конкурентных `users.create`. Migration wipe (если в secure storage сохранён старый mismatched `pb_user_id` — стирает creds и заново регистрирует под правильным id). Валится с `StateError` если сервер вернул другой id — ранний детектор регрессии контракта.
5. **`ensureAuth` ДО `subscribe` в `IncomingCallSignalingService.start()`.** Одна строка, но без неё фикс identity бесполезен.
6. **`CallManager` кормит resolver UUID-ами контактов.** `_knownContactUuidsCache` обновляется перед `start()` глобального listener-а; передаётся как `knownPeerUuidsProvider`.
7. **Bundled secondary: TURN empty-creds guard.** Web RTC-стек кидает `TURN server with empty username or password` если для `turn:/turns:` URL не задан username/password. И native, и web media bindings теперь скипают такую запись с `debugPrint`, не разрушая call setup (STUN fallback продолжает работать).
8. **Documentation alignment.** `docs/POCKETBASE_SETUP.md` обновлён: 15-char SHA-256 derivation, migration note для legacy установок, объяснение `creatorUuid` в payload. `docs/SECURITY.md` — note что hash односторонний, но UUID всё ещё виден оператору PocketBase через payload. `.ai-factory/DESCRIPTION.md:16` — обновлён identity contract.
9. **Тесты.** `pb_user_id_test.dart` переписан под новый контракт: pinned hash, length-15 invariant, resolver round-trip/passthrough/`empty` no-op. `rtc_message_test.dart` — `fromRecord` с/без resolver-а. `pw-test/two-browser-call.mjs` — переход на paste contact bundle вместо голого UUID (без bundle `searchUsers` не находит контакт) + capture browser-логов A/B для post-mortem.

## Prevention

- **Не доверяй чужой документации сторонних сервисов.** Документация PocketBase про custom id format была неверной/двусмысленной («длина 15+»). Контракты на границе с внешним сервисом нужно проверять эмпирически и пинить тестом. Любая бинарная зависимость может изменить формат — pinned test ловит регрессии и со стороны сервиса.
- **`StateError` на mismatched identity сразу после регистрации.** Если бы прежняя реализация валилась на первом запуске при `auth.record.id != expectedPbId` — баг был бы поймал в день введения. Сделано в `PocketBaseAuthService._doEnsureAuth` post-condition.
- **Lossy mapping требует pull-side контекста.** Когда заменяешь bijection на surjection (hash), обязательно проследить downstream-цепочки, где обратное преобразование считалось возможным. В нашем случае: `message.creator == knownContactUuid` — пришлось вводить resolver и payload-fallback.
- **Order matters: auth before subscribe.** SSE realtime API привязывает identity на handshake. Любой `subscribe(...)` без предварительного `ensureAuth` на сервере с listRule на `auth.id` — мёртвая подписка. Регрессий-тест: расширить `pocketbase_signaling_smoke_test.dart` сценарием «callee, оба варианта порядка вызовов» — must pass только при auth→subscribe.
- **Shared singletons требуют shared in-flight guard.** Локальный `Future? _authInFlight` внутри сервиса не защищает от другого сервиса, использующего тот же PocketBase singleton. Любой shared client = shared auth lifecycle.
- **Empty external credentials не должны идти в bindings.** WebRTC peer connection крайне нетерпим к invalid ICE servers. Любые env-driven конфиги (TURN, STUN) обязаны валидировать сразу при формировании списка, а не передавать «как есть» с надеждой что компонент разберётся.
